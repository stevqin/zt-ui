# Zt UI API 文档重构设计

## 目标

参考 Element Plus 的组件文档阅读方式，重构 Zt UI 全部 38 个稳定组件的 API 信息模型、生成流程和页面呈现。使用者应能在一个组件页面内完成“理解用途、运行示例、查阅接口、确认类型”的完整阅读过程，不再依赖分离的示例页与 API 详情页。

## 路由与阅读路径

- `/:component` 是组件文档的唯一详情路由。
- 组件页面按照“用途说明 → 场景示例 → API → 类型声明”的顺序连续呈现。
- 删除 `/api/:component` 路由，不提供重定向或兼容页。
- `/api` 保留为全部稳定组件的 API 索引，点击组件后进入 `/:component#api`。
- Header、全站搜索、组件全景、场景方案和路线图继续使用现有站点框架。
- 全站搜索中的属性、事件、插槽、方法与类型结果链接到 `/:component#<api-anchor>`。

## API 信息结构

每个组件及其组合子组件分别展示以下分区：

1. **属性 Attributes**
   - 模板名称，例如 `model-value`、`border-radius`。
   - Vue/TypeScript 名称，例如 `modelValue`、`borderRadius`。
   - 中文说明。
   - 精确类型。
   - 精确默认行为。
   - 必填标记。

2. **事件 Events**
   - 事件名称。
   - 触发时机与用户动作。
   - 完整回调签名，包括参数名称和类型。
   - 与 `v-model` 的对应关系。

3. **插槽 Slots**
   - 插槽名称。
   - 使用场景。
   - 作用域参数的完整对象结构；无参数时明确标为“无”。

4. **公开方法与属性 Exposes**
   - 区分 `method` 与 `property`。
   - 展示完整签名或属性类型。
   - 说明返回值、异步行为、状态变化和主要副作用。

5. **类型声明 Types**
   - 优先展示公共导出类型。
   - 依赖类型折叠展示，并明确其不能直接导入时的状态。
   - 避免把组件内部实现类型当成公共 API。

## 默认值语义

API 文档不再使用含混的“未设置”。生成结果只能使用以下明确状态：

- 实际字面默认值，例如 `false`、`[]`、`primary`。
- `必填`：调用方必须提供。
- `无默认值`：可选且省略后为 `undefined`。
- `继承 ConfigProvider`：说明继承字段及最终回退值。
- `运行时计算`：说明决定结果的输入或上下文。
- `受组合组件控制`：说明由父组件或表单上下文提供。

函数和对象默认值展示对使用者有意义的结果，例如 `[]`、`{}`，不展示源码箭头函数包装。

## 文档数据来源

采用“源码提取 + 强类型元数据覆盖”的混合方案：

- 生成器继续从 Vue Props、Emits、Slots、`defineExpose` 和 TypeScript 声明中提取名称与签名。
- 新增按组件维护的文档元数据，补充源码无法表达的业务语义、触发时机、默认行为和副作用。
- 元数据使用 TypeScript 类型约束，属性、事件、插槽和方法名称必须与生成器提取结果匹配。
- 生成时合并源码结构和人工语义；不存在的元数据键会直接报错，避免拼写错误和失效说明。
- 公共类型仍由组件导出声明决定，不通过文档元数据虚构接口。

建议将职责拆分为：

- `site/scripts/api/collect.mjs`：读取组件源码和类型声明。
- `site/scripts/api/metadata.ts` 或等价数据目录：维护精确中文语义。
- `site/scripts/api/validate.mjs`：执行完整性检查。
- `site/scripts/generate-api.mjs`：编排提取、合并、校验和 JSON 输出。
- `site/src/components/ApiReference.vue`：呈现单个组件的 API 分区。
- `site/src/components/ApiTable.vue`：呈现桌面表格和移动端卡片。

## 页面呈现

- API 区域使用统一标题层级：`API` → 组件/子组件名称 → Attributes / Events / Slots / Exposes / Types。
- 属性表优先使用“名称、说明、类型、默认值”列序，便于先理解用途。
- 类型保持等宽字体，并允许展开长类型；不以截断或横向滚动作为唯一阅读方式。
- 每个 API 项生成稳定锚点，悬停或聚焦时提供锚点复制入口。
- 组件页右侧目录包含示例章节和 API 分区，并随滚动更新。
- 组合组件分别形成清楚的小节，例如 `Form`、`FormItem`、`FormGroup`。
- 没有事件、插槽或 Exposes 的空分区不渲染，减少无效内容。
- 桌面端使用紧凑表格；窄屏改为键值卡片，避免依赖横向滚动。
- Light、Dark、五档 size 与 borderRadius 继续作用于整个文档站。

## 文案标准

- 描述具体行为，避免“用于设置”“相关配置”“具体见示例”等循环说明。
- 布尔属性统一回答启用后发生什么。
- 回调说明统一回答何时调用、参数是什么、返回值如何影响组件。
- `object`、`array`、`Function` 等宽泛类型必须链接或展开为具体公共类型。
- `v-model` 属性明确值结构、空值和清空后的结果。
- 时间、尺寸、像素、索引等数值明确单位和边界。
- 异步接口明确 Promise 的完成和失败语义。

## 完整性门禁

生成器必须阻止以下内容进入构建产物：

- 缺少中文说明的 Props、Events、Slots 或 Exposes。
- 默认值仍为“未设置”或无法解释的源码表达式。
- 只写 `Function`、`object`、`array` 而没有具体签名或引用类型。
- 元数据引用不存在的 API 名称。
- 稳定组件缺少 API 文档。
- 搜索结果仍指向已删除的 `/api/:component`。

## 测试与验收

- 生成器单元测试覆盖默认值归一化、模板名称转换、元数据合并和无效元数据拒绝。
- 文档完整性测试覆盖全部 38 个稳定组件，确保说明、类型和默认值满足门禁。
- 路由测试确认 `/api/:component` 不再注册，组件 API 索引链接到 `/:component#api`。
- 页面测试覆盖普通组件、组合组件、复杂事件、作用域插槽和 Exposes。
- 搜索测试覆盖 Props、Events、Slots、Exposes 和 Types 的新锚点。
- 在桌面、390px 移动端、Light、Dark 下检查 Select、DatePicker、Upload、Form、Modal 和 VTableGrid 六个代表页面。
- 最终运行组件库测试与构建、文档站测试与 GitHub Pages 模式构建。

## 发布结果

重构完成后直接提交到 `main` 并触发 GitHub Pages。发布页面不保留旧 API 详情路由，站内所有入口和搜索结果同步切换到新的组件页锚点。
